실제 사용자 검수에는 [기능 목록과 체크리스트](workspace-review-checklist.md)를 사용한다.

- 2026-11-14: 합의한 전환·이동 기능은 실제 사용자 검수까지 완료. 단일 창 따라가기는 `2221feb`의 두 IPC 호출 방식으로 해결했다.
- 회귀 테스트를 `9504772`에 저장했다. 정상 설정 120개 키 조합 통과, 임시 사본의 세 결함은 기능 검사에서 실패함을 확인했다. 변형 코드는 저장하지 않는다.
- workspaces.conf는 분리하지 않고 다섯 섹션으로 모았다. 유효 명령 보존과 정리 후 120개 회귀 검사, 실행 중 설정과의 유효 명령 동일성 및 임시 mark 없음까지 확인했다.

- Alt+Tab MRU는 별도 후속 논의이고, 출발 모니터 기억(F4)과 내용 교환은 제외한 결정을 유지한다.

- 사용자가 앞선 키패드 실험에서 Num Lock 켜짐·꺼짐 동작을 확인했다. 이후 다시 만든 초기 커밋에는 해당 실험 바인딩이 없고 F1~F10 전환 바인딩이 있다. S0은 새 초기 커밋을 그대로 보존하며 키패드 기능을 복원하지 않는다. 새 키패드 배치와 Shift 조합은 이후 단계에서 별도 검수한다.
- 구현은 [README의 공통 절차](../README.md)에 따라 한 단계씩 커밋하고 사용자 검수를 기다린다.

## 목적과 확정한 동작

양쪽 모니터를 독립적으로 사용할 수 있게 하면서, 키패드로 대응하는 두 워크스페이스를 함께 표시하거나, 현재 양쪽 공간의 창들을 목적지 쌍으로 이동한다. 같은 번호의 쌍은 함께 불러오는 프리셋이며, 평소에는 `F2 + 5`처럼 서로 다른 번호를 자유롭게 조합할 수 있다.

| 구분 | 모니터 | 내부 번호 | 최종 실제 이름 | i3bar 표시 |
|---|---|---|---|---|
| 오른쪽 | HDMI-0 | 1~10 | `1:1` … `9:9`, `10:0` | `1` … `9`, `0` |
| 왼쪽 | DP-1 | 11~20 | `11:F1` … `20:F10` | `F1` … `F10` |

`$right1`~`$right10`, `$left1`~`$left10`처럼 방향을 구분하는 변수를 사용한다. 오른쪽 열 번째 공간은 숫자키 0, 왼쪽 열 번째 공간은 F10, 이 쌍은 키패드 0에 대응한다. 내부 번호로 정렬하고 i3bar의 `strip_workspace_numbers yes`로 표시 접두사를 숨긴다.

| 단축키 | 최종 동작 |
|---|---|
| Mod+숫자 | 오른쪽 공간만 전환 |
| Mod+F키 | 왼쪽 공간만 전환 |
| Mod+Shift+숫자 | 현재 창 하나를 오른쪽 목적지로 이동하고 그 창에 포커스 |
| Mod+Shift+F키 | 현재 창 하나를 왼쪽 목적지로 이동하고 그 창에 포커스 |
| Mod+키패드 숫자 | 대응하는 왼쪽·오른쪽 공간을 함께 표시하고 주 모니터인 오른쪽에 포커스 |
| Mod+Shift+키패드 숫자 | 현재 양쪽 공간의 창들을 목적지 쌍에 각각 합류시키고, 원래 집중하던 창을 따라감 |

개별 창 이동은 현재 창을, Shift+키패드는 현재 양쪽 공간의 모든 창을 목적지에 합류시킨다. 교환 기능은 사용하지 않는다. 목적지의 기존 창은 그대로 남고, 배치는 i3 기본 규칙을 따른다. 창 닫기, 리로드, 방향키 이동 등 다른 Shift 단축키는 별도 요구가 없으면 유지한다.

## 현재 구성과 변경 영향

- 기존 왼쪽: 1, 3, 5, 7, 9 → DP-1.
- 기존 오른쪽: 2, 4, 6, 8, 10 → HDMI-0.
- 숫자 전환키와 Shift 이동키가 기존 `$ws1`~`$ws10`을 참조한다.
- 새 초기 커밋의 F1~F10에 예전 양쪽 전환 명령이 있다. 키패드 바인딩은 없다. 새 바인딩과 중복되지 않도록 해당 단계에서 교체한다.
- `# Ctrl+Tab`이라는 주석 아래의 실제 바인딩은 `Mod1+Tab workspace back_and_forth`, 즉 Alt+Tab이다. MRU 창 전환은 아직 구현하지 않는다.
- Num Lock은 Mod2다. 키패드는 bindcode의 일반 바인딩과 Mod2 바인딩을 둘 다 둔다. Shift 조합도 두 상태를 별도로 검증한다.
- Gammastep, 입력기, 터미널 실행, 잠금, 오디오 등 관계없는 설정은 유지한다.

번호를 변경할 때는 변수뿐 아니라 전환키, 이동키, 모니터 배정, 직접 적힌 번호, 기존 보조 프로그램·앱 배정·bar 참조를 점검한다. 한 커밋 안에서 참조가 끊기거나 중복되는 중간 상태를 만들지 않는다.

## 목표 파일 구성

```text
~/.config/i3/
├── config
├── config.d/
│   ├── base.conf
│   └── workspaces.conf
├── README.md
├── scripts/                 # 보존 중인 일회성 이전 도구
├── tests/                   # 보조 도구 검사
└── docs/
    └── dual-monitor-workspaces.md
```

먼저 두 파일로만 분리한다. 메인 `config`는 `$mod` 등 공통 변수와 명시적인 include 목록을 갖는다. `base.conf`에는 일반 키, 레이아웃, 시작 프로그램, bar를 둔다. `workspaces.conf`에는 워크스페이스 변수·모니터 배정·전환·이동 바인딩을 함께 둔다. 스크립트는 i3 설정만으로 부족한 기능을 구현하는 단계에서만 추가한다.

## 기존 워크스페이스 이전

현재 작업을 보존할 경우 의미상 이전표는 다음과 같다. 아직 존재하지 않는 공간은 전환할 때 만든다.

| 기존 공간 | 새 내부 번호 | 최종 이름 | 모니터 |
|---|---|---|---|
| 1 | 11 | 11:F1 | DP-1 |
| 3 | 12 | 12:F2 | DP-1 |
| 5 | 13 | 13:F3 | DP-1 |
| 7 | 14 | 14:F4 | DP-1 |
| 9 | 15 | 15:F5 | DP-1 |
| 2 | 1 | 1:1 | HDMI-0 |
| 4 | 2 | 2:2 | HDMI-0 |
| 6 | 3 | 3:3 | HDMI-0 |
| 8 | 4 | 4:4 | HDMI-0 |
| 10 | 5 | 5:5 | HDMI-0 |

실행 전 현재 IPC 상태를 읽고 표에 없는 공간이나 이름 충돌이 있는지 확인한다.
기존 이름을 임시 이름으로 옮긴 뒤 새 이름을 부여하는 등 충돌하지 않는 순서를 계획한다.
사용자가 실행할 이전 절차와 리로드를 구분한다. 워크스페이스의 이름 변경·이동은 리로드만으로 이루어지지 않는다.

## 포커스 정책

- 기본 방향키 포커스는 유지한다.
- Shift 없는 키패드 쌍 전환은 왼쪽 목적지를 먼저 표시하고 오른쪽 목적지를 마지막으로 선택한다. 시작 위치와 관계없이 주 모니터인 오른쪽 HDMI-0에 포커스한다.
- 이미 목적지 쌍이 표시되어 있어도 오른쪽에 포커스한다. 각 공간 내 마지막 창 선택은 i3 기본 동작을 사용한다. 출발 모니터 기억 기능(F4)은 사용자 지시로 제외했으므로 이 오른쪽 고정 정책을 유지한다.
- 혼합 조합을 고정 쌍으로 강제하지 않는다. 개별 숫자/F키 전환은 계속 독립적이다.
- 포인터 위치와 기본 focus-follows-mouse 때문에 복원 직후 포커스가 달라지는지도 사용자 검수에 포함한다. 설정을 임의로 바꾸지 않는다.

## 쌍 이동의 의미와 경계 조건

현재 F2+5에서 Shift+키패드3을 누르면 F2의 모든 창을 F3에, 5의 모든 창을
3에 보낸다. F3/3에 있던 기존 창은 그대로 남는다. 마지막에는 F3+3을 표시하고
처음 집중하던 창에 포커스한다. 교환은 하지 않는다.

- 창을 목적지에 합류시키므로 기존 작업의 중첩 split이나 tabbed 구조를 통째로 보존하지 않는다.
- floating은 유지하며 배치는 i3 기본 동작을 따른다. 일반 fullscreen도 가상 환경에서 확인했다.
- 목적지가 이미 현재 공간이면 `--no-auto-back-and-forth`로 다른 공간으로 되돌아가지 않는다.
- 처음 창에 `_i3_move_follow`라는 임시 mark를 추가하고 마지막에 그 창을 포커스한 뒤 제거한다. 기존 사용자 mark는 유지한다. 이 이름은 설정의 내부 예약 mark로 사용한다.
- 빈 출발 공간에는 옮길 창이 없다. 처음 포커스된 공간이 비어 원래 창이 없으면 최종 오른쪽 목적지의 i3 기본 포커스가 남는다.
- 빈 공간에 대한 criteria 이동이나 사라진 mark 포커스는 i3 로그에 무대상 오류를 남길 수 있다. 후속 명령은 계속 실행되며 가상 환경에서 최종 상태를 확인했다.
- 창이 스스로 닫히거나 포커스를 바꾸는 경우 원래 창 복원은 보장되지 않는다.
- 두 출력 DP-1/HDMI-0이 연결된 환경을 전제로 한다. 이 직접 명령에는 출력 분리 감지나 별도 오류 처리 도구를 두지 않는다.
- 이동 후 다시 같은 키를 누르면 현재 목적지 안에서 이동하므로 교환처럼 내용이 되돌아가지 않는다.

## 자동 검사와 사용자 적용

- 매 단계 `git diff --check`와 `i3 -C -c ~/.config/i3/config`를 수행한다.
- 키 충돌, 번호/이름/출력의 일관성, include 참조를 확인한다. 실제 수정키 매핑이 필요한 검사는 X11 접근이 가능한 환경에서 수행한다.
- 스크립트가 필요한 단계에서는 빈 목적지, 동일 목적지, 포커스 대상 부재, 명령 실패 등 의미 있는 동작을 검증한다.
- 실제 창 이동·교환·포커스 전환·리로드는 사용자가 실행하고 검수한다. 자동 검증 완료와 사람이 확인한 결과를 구분한다.
- 단계별 안내에는 커밋, 변경 범위, 사용자가 실행할 명령, 최소 재현 순서, 기대 결과, 복구 절차를 포함한다.
- workspace 번호·이름이 바뀌어도 빈 공간 20개가 항상 bar에 나타나는 것은 아니다. i3는 비어 있고 표시되지 않는 공간을 제거할 수 있다.

## 이번 범위 밖 / 후속 논의

- 현재 양쪽에 표시된 두 워크스페이스 안의 창만 최근 사용 순서로 전환하는 Alt+Tab. 두 화면 기본 전환·이동이 안정된 뒤 별도 계획과 검수로 진행한다.
- 브라우저 탭, Herdr pane 등 앱 내부 요소는 i3 창 전환 대상과 구분한다.
- 재부팅 후 앱 실행과 창 배치까지 복구하는 세션 복원은 이번 범위에 포함하지 않는다. 쌍 전환 시 출발 모니터나 쌍별 마지막 창을 별도로 기록하는 기능도 이번 범위에서 제외한다.

### S0 사용자 검수 절차

1. `i3-msg reload`를 직접 실행한다. 오류 표시가 없고 기존 창·작업 공간·bar가 유지되는지 확인한다.
2. `Mod+1`, `Mod+2`로 기존 번호의 공간을 전환한다. 이번 단계는 여전히 홀수는 왼쪽, 짝수는 오른쪽이다.
3. `Mod+F1`, `Mod+F2`로 기존처럼 1+2 쌍이 표시되고 각각 왼쪽·오른쪽에 포커스하는지 확인한다. 아직 F1이라는 공간 이름은 생기지 않는다.
4. 임시 터미널 하나로 `Mod+Shift+숫자` 이동과 기존 방향키 포커스를 확인한다. 이동한 공간으로 자동 따라가기는 아직 없다.
5. 기존 시작 프로그램이 새로 중복 실행되지 않는지 확인한다. 필요하면 `i3 --moreversion`으로 메인 파일과 포함 파일 두 개가 표시되는지 확인한다.

문제가 있으면 S0 커밋만 `git revert`한 뒤 다시 리로드한다. S0은 런타임 워크스페이스 이름이나 창 위치를 자동 변경하지 않았으므로 별도 이름 이전 복구는 필요하지 않다. 검수 중 사용자가 옮긴 창은 별도로 되돌린다.

### N1 적용 및 사용자 검수

이번 단계는 내부 번호만 바꾼다. `$left1`~`$left10`은 11~20,
`$right1`~`$right10`은 1~10이다. 기존 공간에 해당하는 각 방향 5개만
출력 배정을 유지하며 나머지 배정은 P1에서 추가한다. 표시 문자열은 P2,
새 단축키 배치는 F1에서 적용한다.

기존 숫자키의 작업 대상은 유지된다. 예를 들어 `Mod+1`은 예전 왼쪽 1의
작업(새 11), `Mod+2`는 예전 오른쪽 2의 작업(새 1)을 표시한다.
F1/F2 역시 기존 쌍을 표시하고 각각 왼쪽/오른쪽에 포커스한다.
Shift 이동도 이 대응을 따른다. 아직 이동한 창을 따라가지 않는다.

설정 리로드만 먼저 하지 말고 다음 도구로 이전한다. 기본 실행은 미리보기다.

```bash
python3 ~/.config/i3/scripts/migrate-workspace-numbers.py
python3 ~/.config/i3/scripts/migrate-workspace-numbers.py --apply
```

도구는 기존 이름·출력·활성 설정을 검사한 뒤 **전체 임시 이름 → reload →
새 번호** 순서로 적용한다. 이름 충돌과 이전 출력 배정 규칙의 개입을 피한다.
i3에서는 `__`로 시작하는 이름이 금지되어 있어 임시 이름은 `n1-migrate-`로 시작한다.
창 컨테이너를 다시 만들거나 다른 공간에 합류시키지 않는다. 적용 후 공간 ID,
모니터, 표시 여부, 포커스를 비교한다. 실행 중에는 다른 전환·이동 조작을 피한다.
여러 IPC 명령은 원자적이지 않다. 실패하면 다시 실행하지 말고 출력과
`/tmp/i3-n1-*.json` 중 실행 시 안내한 스냅샷으로 현재 상태를 확인한다.

검수:

1. 적용 성공 메시지 확인. 예전 왼쪽 1은 11, 오른쪽 2는 1로 보이고 기존 창과 배치가 유지되는지.
2. `Mod+1`, `Mod+2`로 기존 작업이 각 화면에 나타나는지.
3. `Mod+3`, `Mod+4`는 왼쪽 12, 오른쪽 2인지. F1/F2로 11+1 쌍 복귀와 포커스 확인.
4. 임시 창 하나를 `Mod+Shift+3`으로 왼쪽 12에 보낸 뒤 `Mod+3`으로 확인.
5. 0번 키는 아직 기존 오른쪽 마지막 공간인 새 5로 가는지. F키도 기존 쌍 전환을 유지하는지.

적용 전 복구는 N1 커밋을 revert하면 된다. 적용 후 되돌리려면 먼저 도구를
`/tmp`에 보존하고 N1 커밋을 revert한 다음, **별도 리로드 없이** 역방향 이전한다:

```bash
cp ~/.config/i3/scripts/migrate-workspace-numbers.py /tmp/i3-n1-rollback.py
# 아래 <N1-commit>은 이번 N1 커밋 해시로 대체한다.
git -C ~/.config/i3 revert <N1-commit>
python3 /tmp/i3-n1-rollback.py --reverse --apply
```

역방향도 예상하지 못한 이름이나 출력이 있으면 중단한다. 이후 단계가 이미
적용되었다면 이 N1 전용 복구 절차를 그대로 실행하지 않는다.

N1 자동 검사: 이전 순서·전체 10개 번호 충돌·역방향 대응·이름/출력 거부·
상태 보존 검증을 단위 검사한다. 실환경에서는 미리보기와 i3 구문 검사만
실행하고 실제 이전·리로드는 사용자가 수행한다.

### P1 적용 및 사용자 검수

각 방향 6~10번째 슬롯의 출력 배정을 추가한다. 오른쪽 내부 번호 1~10은
HDMI-0, 왼쪽 11~20은 DP-1이다. 단축키·표시 이름·열린 창은 그대로 둔다.
이전 N1 이름 이전 도구는 다시 실행하지 않는다.

다음 명령은 리로드 후 양쪽 마지막 슬롯을 표시한다:

```bash
i3-msg 'reload; workspace number 10; workspace number 20'
```

1. 왼쪽에 20, 오른쪽에 10이 표시되는지 확인한다. 아직 F10/0 표시는 아니다.
2. `Mod+F1`로 왼쪽 11, 오른쪽 1과 기존 작업으로 돌아온다.
3. 기존 숫자·F키·Shift 이동의 동작이 유지되는지 확인한다.

빈 공간은 떠나면 bar에서 사라질 수 있다. 모든 20개 공간이 상시 표시되지는 않는다.
문제가 있으면 이 P1 커밋만 `git revert`한 뒤 `i3-msg reload`한다.
검수에서 만든 공간은 비어 있으면 다른 공간으로 전환하면서 사라진다.

### P2 적용 및 사용자 검수

실제 이름을 오른쪽 `1:1`~`9:9`, `10:0`, 왼쪽 `11:F1`~`20:F10`으로
바꾸고 bar에서 번호 접두사를 숨긴다. 내부 번호는 유지하므로 숫자 순서대로
정렬된다. 단축키의 변수 참조는 그대로다. 아직 Mod+숫자와 Mod+F키의 새 배치는 아니다.

열린 공간의 이름 변경과 reload를 함께 적용한다:

```bash
python3 ~/.config/i3/scripts/label-workspaces.py --apply
```

`--apply` 없이 실행하면 미리보기만 출력한다. N1 이전 도구는 다시 실행하지 않는다.
P2 도구는 번호·이름·출력·활성 설정을 검사하고 `/tmp/i3-p2-*.json` 스냅샷을
저장한다. 적용 뒤 공간 ID·내부 번호·출력·표시 여부·포커스 보존을 확인한다.
이미 올바른 이름인 공간은 건너뛴다. 실행 중 다른 공간 전환이나 창 이동은 피한다.
IPC 일부 실패 시 스냅샷과 현재 상태를 확인한다.

검수 순서:

1. 현재 열린 왼쪽 공간이 F로 표시되고 오른쪽은 숫자로 표시되는지.
2. `Mod+1`은 왼쪽 F1, `Mod+2`는 오른쪽 1, `Mod+3`은 왼쪽 F2인지.
3. `i3-msg 'workspace number 10; workspace number 20'`을 실행하여
   왼쪽 F10·오른쪽 0 표시를 확인한다. 아직 Mod+0은 오른쪽 5로 간다.
4. `Mod+F1`로 F1+1 쌍에 복귀하고 기존 창·배치가 유지되는지 확인한다.
5. 공간이 여러 개 존재할 때 F2가 F10보다 앞이고, 오른쪽 0이 9 다음에 오는지 확인한다.
   빈 공간은 떠나면 사라질 수 있으므로 모든 이름이 상시 나타나지는 않는다.

적용 전에는 P2 커밋 revert만 하면 된다. 적용 후 복구는 도구를 먼저 보존하고
P2 설정을 revert한 뒤 역방향으로 이름을 되돌린다:

```bash
cp ~/.config/i3/scripts/label-workspaces.py /tmp/i3-p2-rollback.py
git -C ~/.config/i3 revert <P2-commit>
python3 /tmp/i3-p2-rollback.py --reverse --apply
```

`<P2-commit>`은 이번 P2 커밋 해시다. 이후 단계까지 적용했다면 이 단계 전용
복구 절차를 그대로 사용하지 않는다.

### F1 적용 및 사용자 검수

`Mod+1`~`Mod+9` 및 `Mod+0`은 오른쪽 1~9·0만 전환한다.
`Mod+F1`~`Mod+F10`은 왼쪽 F1~F10만 전환한다.
기존 F키의 양쪽 쌍 전환 명령은 교체했다. 쌍 전환은 F2/F3 단계에서
키패드에 추가한다. 따라서 이번 검수에서는 F키로 양쪽을 함께 전환하지 않는다.

이전 스크립트와 테스트는 사용자의 유지 지시에 따라 그대로 보존한다.
이번 단계에는 새 스크립트를 추가하지 않는다. 적용은 리로드만 필요하다:

```bash
i3-msg reload
```

검수:

1. `Mod+F1`, `Mod+1`로 F1+1을 표시한다.
2. `Mod+2`를 누르면 오른쪽만 2로 바뀌고 왼쪽 F1은 유지되는지.
3. `Mod+F3`을 누르면 왼쪽만 F3으로 바뀌고 오른쪽 2는 유지되는지.
4. `Mod+0`으로 오른쪽 0, `Mod+F10`으로 왼쪽 F10을 확인한다.
5. 나머지 숫자/F키도 각 표시와 대응하는지 확인한다.

Shift 창 이동은 M1/M2 단계까지 이전 대응을 유지하므로, 현재 전환키와
목적지가 다를 수 있다. 예를 들어 `Mod+Shift+1`은 여전히 왼쪽 F1으로
창을 보낸다. 이번 단계에서 이동·따라가기 동작을 변경하지 않는다.

문제가 있으면 이번 F1 커밋만 revert한 뒤 리로드한다. 번호·이름 이전은 필요 없다.

### F2 적용 및 사용자 검수

주 모니터는 오른쪽 HDMI-0이다. `Mod+키패드1`은 왼쪽 F1을 먼저 표시하고
오른쪽 1을 마지막으로 선택한다. 시작한 모니터와 관계없이 항상 오른쪽에
포커스한다. 이미 F1+1이 표시되어 있어도 오른쪽으로 포커스한다.

Python 쌍 전환 스크립트와 해당 전용 테스트는 제거했다. config에 직접 다음
명령을 연결한다. Num Lock 두 상태를 위해 일반/Mod2 바인딩을 함께 둔다.

```i3
bindcode $mod+87 workspace --no-auto-back-and-forth number $left1; workspace --no-auto-back-and-forth number $right1
bindcode $mod+Mod2+87 workspace --no-auto-back-and-forth number $left1; workspace --no-auto-back-and-forth number $right1
```

`--no-auto-back-and-forth`는 반복 입력 시 다른 공간으로 되돌아가는 것을 막는다.
별도 프로세스·서비스·잠금 파일·사용자 포커스 기록은 사용하지 않는다.
기존 N1/P2 일회성 이전 도구와 전용 테스트는 앞선 사용자 유지 지시대로 보존한다.
나머지 키패드도 F3에서 같은 오른쪽 고정 정책으로 확장한다. Shift 쌍 이동은
X1/X2에서 양쪽 합류 이동과 원래 창 따라가기로 처리한다.

적용:

```bash
i3-msg reload
```

검수:

1. `Mod+F2`, `Mod+5`로 F2+5를 표시한 뒤 `Mod+키패드1`:
   F1+1이 표시되고 오른쪽 1에 포커스하는지.
2. 다시 F2+5를 만든 뒤 `Mod+F2`로 왼쪽에 포커스하고 같은 키:
   이번에도 오른쪽 1에 포커스하는지.
3. Num Lock을 반대로 바꿔 1~2를 반복한다.
4. 이미 F1+1에서 `Mod+F1`로 왼쪽을 선택하고 키패드1을 누르면
   오른쪽에 포커스하는지. 반복 입력해도 다른 쌍으로 돌아가지 않는지.
5. 포인터를 움직이지 않은 상태에서 포커스 테두리로 확인한다.

현재 수정 커밋을 revert하면 이전 Python 구현이 돌아온다. F2 도입 전체를
취소하려면 수정 커밋과 `77a3786`을 최신 순서대로 revert한 뒤 리로드한다.
번호·이름 이전이나 창 이동 복구는 필요 없다.

### F3 적용 및 사용자 검수

키패드 전체를 같은 직접 명령 방식으로 확장했다. 공통 주석 하나만 두며
쌍별 주석은 추가하지 않는다. 새 스크립트는 없다. 모든 쌍 전환은 왼쪽 공간을
먼저 표시한 뒤 오른쪽 공간에 포커스한다. Shift 키패드는 아직 추가하지 않았다.

| 키패드 | 키코드 | 왼쪽 | 오른쪽 |
|---|---|---|---|
| 1 | 87 | F1 | 1 |
| 2 | 88 | F2 | 2 |
| 3 | 89 | F3 | 3 |
| 4 | 83 | F4 | 4 |
| 5 | 84 | F5 | 5 |
| 6 | 85 | F6 | 6 |
| 7 | 79 | F7 | 7 |
| 8 | 80 | F8 | 8 |
| 9 | 81 | F9 | 9 |
| 0 | 90 | F10 | 0 |

적용은 `i3-msg reload`다.

1. Num Lock을 끈 상태에서 `Mod+키패드1~9,0`을 각각 눌러 표와 대응하는지 확인한다.
2. Num Lock을 켜고 반복한다. 각 전환에서 오른쪽에 포커스하는지 확인한다.
3. `Mod+F2`, `Mod+5`로 혼합 조합을 만들고 키패드3으로 F3+3 전환을 확인한다.
4. 이미 선택한 쌍에서 반복해도 다른 쌍으로 돌아가지 않고 오른쪽에 포커스하는지.
5. 개별 숫자/F키 전환이 그대로 독립적으로 동작하는지 확인한다.

복구는 이번 F3 커밋만 revert한 뒤 리로드한다. 그러면 키패드1만 남는다.
F4는 오른쪽 고정 정책으로 취소했으므로, 검수 통과 후 다음 단계는 M1의
오른쪽 개별 창 이동 단축키 변경이다.

### M1 적용 및 사용자 검수

`Mod+Shift+1`~`Mod+Shift+9`는 오른쪽 1~9,
`Mod+Shift+0`은 오른쪽 0으로 현재 포커스된 창을 보낸다.
목적지의 기존 창에 합류하며 교환하지 않는다. 현재 포커스가 왼쪽에 있어도
오른쪽 목적지로 이동한다. i3의 `move container` 명령을 직접 사용한다.
일반 창 하나에 포커스하여 검수한다. 사용자가 상위 컨테이너에 포커스한 경우에는
그 컨테이너가 이동하는 i3 기본 동작을 따른다.

아직 목적지를 표시하거나 이동한 창을 따라가지 않는다(A1에서 추가).
왼쪽 Shift+F키 이동은 M2에서 추가한다. 개별 전환키와 키패드는 유지한다.

적용은 `i3-msg reload`다.

1. 임시 터미널 하나에 포커스하고 `Mod+Shift+3`으로 이동한 뒤,
   `Mod+3`으로 오른쪽 3을 표시해 그 터미널이 있는지 확인한다.
2. 목적지에 창이 있으면 기존 창이 남고 새 창이 합류하는지 확인한다.
3. 왼쪽 F공간의 임시 터미널에서도 같은 이동을 확인한다.
4. `Mod+Shift+0` 이후 `Mod+0`으로 오른쪽 0에 도착했는지 확인한다.
5. 목적지가 숨겨진 공간일 때 이동 직후 자동으로 따라가지 않는지 확인한다.

복구는 이번 M1 커밋만 revert한 뒤 리로드한다. 검수 중 이동한 창은 별도로
원하는 공간으로 되돌린다. 기존 창과 공간 이름은 자동 복원하지 않는다.

### M2 적용 및 사용자 검수

`Mod+Shift+F1`~`Mod+Shift+F10`은 현재 포커스된 창을 왼쪽 F1~F10으로
보낸다. 오른쪽에서 시작해도 왼쪽 목적지로 이동한다. 목적지의 기존 창에
합류하며 교환하지 않는다. 오른쪽 숫자 이동키와 전환·키패드 바인딩은 유지한다.
아직 목적지 표시와 이동한 창 따라가기는 추가하지 않는다.
상위 컨테이너를 직접 포커스한 경우에는 i3 기본 컨테이너 이동을 따른다.

적용은 `i3-msg reload`다. 리로드 후 임시 터미널로 검수한다.

1. 오른쪽 공간의 터미널에서 `Mod+Shift+F3` 후 `Mod+F3`:
   왼쪽 F3에 도착했는지 확인한다.
2. 왼쪽 다른 F공간에서 출발해도 같은 목적지로 도착하는지 확인한다.
3. 목적지에 기존 창이 있어도 기존 창이 남고 새 창이 합류하는지 확인한다.
4. `Mod+Shift+F10` 후 `Mod+F10`으로 왼쪽 F10을 확인한다.
5. 숨겨진 공간으로 보낼 때 자동으로 따라가지 않는지 확인한다.

문제가 있으면 이번 M2 커밋만 revert한 뒤 리로드한다. 검수에서 옮긴 창은
별도로 되돌린다. 다음 단계는 X1의 Shift+키패드1 양쪽 합류 이동이다.

### X1 적용 및 사용자 검수

교환 기능을 제거하고 Shift+키패드1만 i3 기본 합류 이동으로 구현했다.
Python 교환 스크립트와 전용 테스트를 제거했다. 나머지 Shift+키패드는 X2에서
확장한다. 기존 N1/P2 일회성 이전 도구는 이전 사용자 지시대로 유지한다.

config의 직접 명령 순서는 다음과 같다.

1. 이전 내부 mark를 지우고 현재 포커스된 창에 `_i3_move_follow` mark를 추가한다.
2. DP-1을 포커스하고 `[workspace="__focused__"]`의 모든 창을 왼쪽 F1에 보낸다.
3. HDMI-0을 포커스하고 해당 현재 공간의 모든 창을 오른쪽 1에 보낸다.
4. 왼쪽 F1과 오른쪽 1을 표시한다.
5. 임시 mark의 원래 창에 포커스하고 mark를 제거한다.

이동과 표시 명령 모두 `--no-auto-back-and-forth`를 사용한다. 기존 개별
Shift+숫자/F키 이동은 그대로이며 자동 따라가기는 아직 A1/A2에서 추가할 예정이다.

자동 검증에서는 `/tmp`에 xvfb 패키지를 다운로드·압축 해제해 가상 디스플레이
`:193`과 별도 i3(fake-0/fake-1)를 실행했다. 시스템에 패키지를 설치하지 않았고,
현재 실제 i3나 사용자 창을 이동하지 않았다. 테스트가 끝나면 테스트 프로세스를
종료했다. 실제 바인딩 명령에서 출력 이름과 변수를 테스트 설정에 맞춰 치환했다.

실행 스크립트: `/tmp/test-i3-native-pair.py`.
환경 파일: `/tmp/i3-native-pair-test/`. 둘 다 임시 검증 자료이며 운영에 필요 없다.

검증한 실제 시나리오:

- 양쪽 창이 기존 창이 있는 목적지에 합류하고 왼쪽 원래 창 포커스 유지.
- 같은 목적지에서 반복 실행해도 다른 공간으로 이동하지 않으며 오른쪽 원래 창 포커스 유지.
- 한쪽이 이미 목적지인 혼합 조합.
- 양쪽 출발 공간이 비어 있는 경우와 임시 mark 정리.
- 빈/없는 목적지 생성과 포커스.
- tabbed 출발 창 이동과 기존 사용자 mark 보존.
- 일반 fullscreen 창 이동과 원래 창 포커스. floating 유지도 첫 시나리오에서 확인.

Num Lock 두 상태의 바인딩과 실제 config 문법도 검사했다. 키보드 입력은
사용자가 실제 세션에서 검수한다. 적용은 다음 한 줄이다:

```bash
i3-msg reload
```

사용자 검수:

1. F1/1에 기존 창을 두고, F2/2에 구별되는 임시 터미널을 둔다.
2. F2+2를 표시하고 왼쪽 임시 창을 선택한 뒤 `Mod+Shift+키패드1`:
   양쪽 임시 창이 각각 F1/1에 합류하고 원래 왼쪽 창에 포커스하는지.
3. 목적지의 기존 창이 그대로 남았는지, 이동한 모든 창이 보이는지 확인한다.
4. 다른 임시 창들로 오른쪽 포커스 출발, Num Lock 두 상태를 확인한다.
5. 이미 F1+1인 상태에서 반복해도 다른 공간으로 이동하지 않는지 확인한다.

복구: 이번 수정 커밋을 revert하면 이전 Python 교환 구현이 돌아온다.
이번 이동 자체는 자동으로 되돌리지 않는다. 목적지 기존 창과 합류했으므로
되돌릴 때는 검수에서 옮긴 창들을 개별 Shift+F키/숫자로 원래 공간에 보낸다.
모든 목적지 창을 함께 되돌리면 원래 목적지에 있던 창까지 이동하므로 피한다.

[mark와 focus](https://i3wm.org/docs/userguide.html#vim_like_marks),
[기본 공간 이동](https://i3wm.org/docs/userguide.html#_changing_named_workspaces_moving_to_workspaces).

### X2 적용 및 사용자 검수

`Mod+Shift+키패드1`~`9`는 현재 양쪽 창을 F1+1~F9+9로,
`Mod+Shift+키패드0`은 F10+0으로 합류 이동한다. 전부 임시 mark로 원래
집중하던 창을 따라간다. 목적지의 기존 창은 유지하며 교환하지 않는다.
Shift 없는 키패드는 이전과 같이 쌍 표시 후 오른쪽 고정 포커스다.

긴 명령은 i3의 줄 이어쓰기로 나눴다. 쌍마다 주석을 반복하지 않고 공통
주석만 둔다. 공통 문자열은 같은 파일의 다음 세 변수에 둔다:

- `$move_focus_begin`: 이전 내부 mark 정리와 현재 창 mark 추가.
- `$pair_move_all`: 현재 포커스된 공간의 모든 창 이동 명령 앞부분.
- `$move_focus_end`: 원래 창 포커스 복원과 내부 mark 제거.

i3에는 인자를 받는 사용자 함수가 없다. `set`은 문자열 치환이며 재귀 확장이
안 되므로 공통 변수 값 안에 다른 변수를 넣지 않는다. 각 바인딩에서 공통
변수와 `$leftN`/`$rightN`을 직접 참조한다. 줄 끝 역슬래시 뒤에 공백이나
주석을 두지 않는다. 함수처럼 숨기기보다 모니터와 목적지 순서가 드러나게 둔다.

자동 검증: `/tmp/test-i3-pair-keys.py`가 `/tmp/i3-native-pair-test/`의 가상
X 서버와 별도 i3에서 실제 workspaces.conf를 읽는다. 출력 이름만 fake-0/1로
대체한다. 라이브러리 XTest로 Super+Shift+각 키패드의 실제 키 이벤트를 보내고
Num Lock을 두 상태로 설정했다. 20개 조합 모두 목적지 기존 창 유지·양쪽 합류·
왼쪽/오른쪽 원래 창 포커스·임시 mark 정리·목적지 쌍 표시를 통과했다.
실제 데스크톱의 창이나 키 입력은 변경하지 않았으며 테스트 프로세스는 종료했다.

적용:

```bash
i3-msg reload
```

사용자 검수:

1. 구별되는 임시 창들로 다른 쌍에서 `Mod+Shift+키패드3`을 눌러 F3+3으로 합류하는지.
2. 왼쪽·오른쪽 각각에서 출발해 원래 집중하던 창을 따라가는지.
3. 키패드0으로 F10+0을 확인하고, Num Lock 두 상태에서 나머지 키도 확인한다.
4. 목적지의 기존 창은 남고, 이미 목적지에서 반복해도 다른 곳으로 가지 않는지.

이번 커밋 revert 후 reload하면 Shift+키패드1만 있던 상태로 돌아간다.
이미 이동한 창은 별도로 개별 이동키로 되돌린다. 자동 역교환은 없다.

후속 작업 A1/A2는 사용자 요청대로 별도로 유지한다. Shift+숫자/F키로 단일
창을 이동할 때도 목적지를 표시하고 방금 옮긴 창에 정확히 포커스하도록
구현·검수할 예정이다. 쌍 이동의 mark 포커스 유지는 이번 X2에 포함되어 있다.

참고: [변수](https://i3wm.org/docs/userguide.html#variables),
[줄 이어쓰기](https://i3wm.org/docs/userguide.html#_line_continuation).

## 남은 작업과 제외한 추가 피처

A1/A2까지 사용자 검수 완료. 합의한 기능 구현은 끝났으며 최종 검수와 별도 후속 논의를 구분한다.
이 문서 갱신에서는 config를 바꾸거나 리로드하지 않는다.

| 항목 | 요구 | 현재 상태 |
|---|---|---|
| A1 | Shift+숫자로 단일 창을 오른쪽에 보낸 뒤 목적지를 표시하고 방금 옮긴 창에 포커스 | 완료·별도 IPC 방식으로 실제 단축키 사용자 검수 통과 |
| A2 | Shift+F키로 단일 창을 왼쪽에 보낼 때도 같은 따라가기 | 완료·별도 IPC 방식으로 실제 단축키 사용자 검수 통과 |
| F4 | Shift 없는 키패드 쌍 전환에서 출발 모니터 쪽 유지 | 사용자 지시로 제외. 현재 오른쪽 고정 포커스 유지 |
| R1 | 전체 회귀 검수와 재로그인 검수 | 기능 완료 후 Num Lock·혼합 쌍·빈 공간·mark 정리·시작 프로그램 확인 |
| 별도 후속 | 현재 표시된 두 공간 안의 창을 MRU 순서로 전환하는 Alt+Tab | 아직 구현 범위 밖. 위 작업 안정화 뒤 별도 설계·검수 |

### F4 제외 결정과 이유

사용자가 원한 추가 동작은 Shift 없는 키패드 쌍 전환에서 **출발한 모니터 쪽
유지**다. 예를 들어 F1 왼쪽에서 키패드3을 누르면 F3에 포커스하고,
오른쪽 1에서 시작하면 오른쪽 3에 포커스하는 것이다. 쌍별 마지막 창 복원과는
다른 요구로 확인했다.

검토 과정에서 다음을 구분했다.

- i3의 `set`은 설정 로드 시 문자열 치환이다. 현재 출력 이름을 읽어 실행 중 변수에 저장하는 기능이 아니다.
- mark는 창/컨테이너의 이름표다. Shift 쌍 이동에서는 그 창이 목적지로 함께 이동하므로 mark로 따라갈 수 있다.
- Shift 없는 전환에서는 원래 창이 이전 공간에 남는다. 그 mark를 무조건 포커스하면 이전 공간으로 돌아갈 수 있어, 이동용 mark 처리를 그대로 재사용하지 않는다.
- 확실한 외부 도구 방식은 `get_workspaces`에서 focused 공간의 output을 읽고, 목적지 쌍 표시 후 원래 output을 포커스하는 것이다. Python은 필수가 아니며 셸과 jq로도 가능하다.
- 이를 i3의 실행 중 변수 저장 기능이나 단순한 고정 명령으로 구현할 수 있다고 단정하지 않는다. 앞선 설명에서 가능 여부를 검증 없이 확정한 부분은 바로잡았다.

사용자는 이 정도의 편의를 위해 외부 스크립트·jq 의존성과 유지보수 코드를
추가할 필요가 작다고 판단했다. **i3 기본 명령으로 되는 수준만 사용**하기로
결정하여 F4를 구현하지 않는다. 이 결정은 기술적으로 전체 기능이 불가능하다는
의미가 아니라, 추가 복잡도 대비 편익을 고려한 범위 선택이다.

현재 동작은 계속 다음과 같다.

- `Mod+키패드`: 목적지 쌍 표시 후 항상 오른쪽 주 모니터 포커스.
- `Mod+Shift+키패드`: 양쪽 창들을 목적지 쌍에 합류 이동하고 mark로 원래 창 따라가기. 구현·검수 완료.
- 쌍별 마지막 창을 저장하는 별도 기능도 이번 범위에 추가하지 않는다.

A1/A2는 같은 mark 처리와 검수 패턴이므로 사용자 요청에 따라 함께 구현했다. 두 기능의 사용자 검수 후 R1 전체 검수를 진행한다.
현재 두 화면 안의 창만 대상으로 하는 Alt+Tab MRU는 별도 후속 논의로 유지하며,
이를 i3 기본 명령만으로 구현 가능하다고 미리 가정하지 않는다.

### A1/A2 함께 적용 및 사용자 검수

사용자가 양쪽 따라가기를 함께 구현할 수 있는지 요청했고, 같은 방식이므로
A1/A2를 하나의 변경 단위로 구현했다. 별도 스크립트 없이 i3 기본 명령을 사용한다.

- Shift+숫자: 현재 포커스된 창을 오른쪽 해당 공간으로 보낸 뒤 그 창 따라가기.
- Shift+F키: 현재 포커스된 창을 왼쪽 해당 공간으로 보낸 뒤 그 창 따라가기.
- 목적지에 기존 창이 있으면 합류하고, 기존 창이 아닌 방금 이동한 창을 포커스한다.
- 목적지 쪽 공간만 전환한다. 반대 모니터의 표시 공간과 다른 창은 그대로 둔다.

공통 변수 `$move_focus_begin`과 `$move_focus_end`를 첫 이동 바인딩보다 앞에
정의했다. 현재 창에 내부 mark `_i3_move_follow`를 추가하고, 이동과 목적지
표시 후 mark로 그 창에 포커스하고 제거한다. 기존 사용자 mark는 `--add`로
보존한다. 앞선 쌍 이동의 begin/end 변수와 내부 mark 이름도 이 공통 이름으로
정리해 단일/쌍 이동이 같은 포커스 처리를 공유한다. `$pair_move_all`은 양쪽
모든 창 이동 전용으로 남긴다. 줄 이어쓰기는 유지한다.

이동과 목적지 표시 모두 `--no-auto-back-and-forth`를 사용하여 같은 목적지에서
다시 눌러도 이전 공간으로 돌아가지 않는다. 상위 split 컨테이너를 직접 선택한
경우에는 i3 기본 컨테이너 이동을 따른다. 따라갈 창이 없거나 이동 중 창이
닫히면 정확한 창 복원은 적용할 수 없다.

자동 검증:

- `/tmp/test-i3-single-follow.py`: 가상 X/i3에서 실제 config를 로드하고
  Shift+숫자 10개, Shift+F키 10개를 Num Lock 두 상태로 실제 키 이벤트 전송.
  총 40개 조합 모두 이동한 창만 정확히 포커스하고 다른 창과 반대 표시 공간은
  보존됨을 확인. 같은 목적지 반복, 사용자 mark 보존, floating·일반 fullscreen도 포함.
- `/tmp/test-i3-pair-keys.py`: 공유 변수·mark 변경 후 기존 쌍 이동 20개 조합 회귀 통과.
- i3 설정 문법과 diff 검사 통과. 실제 사용자 데스크톱에는 리로드나 이동을 하지 않았다.

적용:

```bash
i3-msg reload
```

사용자 검수:

1. 목적지 오른쪽 3에 기존 창을 두고, 다른 공간의 임시 터미널에서
   `Mod+Shift+3`: 오른쪽 3으로 이동하며 그 터미널에 포커스하는지.
2. 오른쪽 임시 창에서 `Mod+Shift+F3`: 왼쪽 F3으로 이동하며 그 창에 포커스하는지.
3. `Mod+Shift+0`과 `Mod+Shift+F10`의 끝 슬롯, 같은 목적지 반복을 확인한다.
4. 반대 모니터의 표시 공간과 다른 창이 유지되는지, 기존 키패드 쌍 이동도 그대로인지.

문제가 있으면 이번 A1/A2 커밋만 revert한 뒤 리로드한다. 검수 중 실제로 옮긴
창은 별도로 되돌린다. 설정 revert는 창의 위치까지 복구하지 않는다.
이 검수 통과 후 남은 것은 R1 전체 회귀 및 재로그인 검수다.

### A1/A2 모니터 간 이동 포커스 복귀 수정

사용자가 오른쪽 1→왼쪽 F1 및 반대 이동에서 창은 옮겨지지만 포커스가
출발 공간에 남는다고 보고했다. 실행 중인 i3의 `get_config.included_configs`로
로드된 바인딩이 디스크와 같음을 확인했으므로 리로드 누락은 아니었다.

실제 i3 로그에서 원래 창에 mark가 붙고, 이동과 목적지 선택 및 mark focus가
실행되는 것을 확인했다. 직후 원래 출력 좌표의 root EnterNotify가 들어오며
출발 공간으로 포커스가 돌아갔다. 초기 가상 검사는 마우스 추적을 꺼 둔
조건이었으므로 실제 사용자 검수를 대신하지 못했다.

수정 순서:

1. 현재 창에 mark를 붙인다.
2. **목적지 공간을 먼저 선택**한다. 출력 전환 시 포인터 이동을 먼저 처리한다.
3. 현재 포커스된 창이 아니라 **mark가 붙은 원래 창을 명시하여** 목적지로 옮긴다.
4. mark가 붙은 창에 포커스하고 mark를 지운다.

이 순서로 바꿔서 이동 직후의 좌표·포인터 처리에 의존하지 않도록 한다.
키패드 쌍 이동과 일반 마우스 포커스 정책은 변경하지 않는다. Python은 사용하지 않는다.

추가 가상 검증은 `focus_follows_mouse yes`에서 출발 창 위에 실제 가상 포인터를
놓고, 키 입력 뒤 잠시 기다려 포커스가 유지되는지 확인했다.
`/tmp/test-i3-single-follow-mouse.py`의 40개 조합과
`/tmp/test-i3-single-follow-empty.py`의 마지막 창·빈 목적지 40개 조합을 검사했다.
원래 구현의 문제가 가상 환경에서 똑같이 재현된 것은 아니므로, 이 통과만으로
실제 세션의 문제가 해결됐다고 확정하지 않고 사용자 재검수를 기다린다.
진단용 i3 메모리·debug 로그는 검사 후 종료했다.

사용자는 리로드 후 임시 창을 `1 → F1`, `F1 → 1`로 각각 보내고,
마우스를 움직이지 않아도 바로 이동한 창에 키보드 입력이 들어가는지 확인한다.
수정 커밋만 revert하면 초기 A1/A2 동작으로 돌아간다. 실제 창 위치는 별도 복구한다.

### A1/A2 재검수 실패 및 기존 구현 조사

사용자가 수정 커밋 `542d1ca` 적용 후에도 모니터 간 이동 포커스가 유지되지
않는다고 보고했다. 원래 출력의 EnterNotify는 관찰했지만, 이를 근본 원인으로
확정하거나 명령 순서 변경으로 해결됐다고 판단하지 않는다. A1/A2는 미완료다.

사용자 요청으로 추가 자체 수정 전에 기존 공개 구현을 조사했다.

| 자료 | 확인된 기능 | 현재 요구와 차이 |
|---|---|---|
| [Regolith i3-next-workspace 소스](https://github.com/regolith-linux/i3-next-workspace/blob/main/i3-next-workspace) | `--move-window-and-follow` 제공. Python/i3ipc로 이동 명령과 공간 전환을 별도 `i3.command()` 호출로 보냄 | 다음 빈 공간 선택용이며 Regolith의 xrdb workspace 이름 매핑을 참조. 현재 F1/1 등 지정한 기존 목적지와 다르므로 그대로 설치해 해결된다고 볼 수 없음 |
| [i3-workspace-groups](https://github.com/infokiller/i3-workspace-groups) | Python 그룹 관리 도구와 workspace 전환/이동 CLI 제공 | 그룹 이름·번호 관리가 핵심. 현재 표시 이름과 그룹 규칙을 바꿀 수 있어 단일 창 포커스 문제 하나를 위해 도입하기에는 범위가 큼. 이 버그 해결은 확인되지 않음 |
| [i3-multimonitor-workspace](https://github.com/J3rome/i3-multimonitor-workspace) | Python/i3ipc 데몬으로 여러 모니터 공간 전환 동기화, 같은 모니터를 유지하는 이동 지원 | 현재 독립 전환과 쌍 프리셋보다 강한 전체 동기화 모델. 프로젝트도 MVP임을 명시하며 현재 문제 해결은 확인되지 않음 |

[i3 #6075](https://github.com/i3/i3/issues/6075)는 모니터 간 키보드 창 이동 후
포커스가 원래 화면에 남는 유사 보고다. 이 보고의 명령은 방향 이동이므로
현재 workspace/mark 명령과 동일 원인이라고 단정하지 않는다.
[i3 #6372](https://github.com/i3/i3/issues/6372)도 포인터가 남는 포커스 문제지만
창 하나가 아닌 workspace의 출력 이동 사례다.

이번 조사 범위에서는 현재 단축키·지정 목적지·실제 포커스 문제까지 그대로
대체한다고 확인한 기성 도구는 찾지 못했다. 그렇다고 공개 구현이 전혀 없다고
단정하지 않는다. 설치·실행 설정 변경은 하지 않았다.

Regolith의 **이동/전환을 서로 다른 IPC 호출로 분리**하는 방식은 다음 최소
수정 후보로 남긴다. 이것이 현재 문제를 고친다는 것은 아직 검증하지 않았다.
기존 배치 전체를 그룹 도구로 교체하기 전에 별도 가상 환경과 실제 사용자
검수로 확인해야 한다. 외부 도구나 스크립트 채택은 기존 i3 기본 명령 우선
방침과의 변경 범위를 설명하고 결정한다.

### A1/A2: 실제 검수된 두 IPC 호출 방식 적용

사용자가 오른쪽 1의 터미널에서 왼쪽 F1로, 이어서 F1에서 오른쪽 1로 보내는
다음 두 호출 방식에 대해 양방향 이동·포커스 유지가 정상이라고 확인했다.

```bash
i3-msg 'unmark _i3_follow_test; mark --add _i3_follow_test; move --no-auto-back-and-forth container to workspace number "1:1"' &&
i3-msg 'workspace --no-auto-back-and-forth number "1:1"; [con_mark="^_i3_follow_test$"] focus; unmark _i3_follow_test'
```

config에는 같은 원리로 Shift+숫자/F키 전체를 적용했다. 운영 mark는 기존
`_i3_move_follow`를 사용한다. 첫 호출에서 mark 추가와 이동을 수행하고,
성공하면 두 번째 호출에서 목적지 표시·mark 포커스·mark 제거를 수행한다.

- `&&`는 i3 기본 명령 연산자가 아니라 **exec가 실행하는 셸의 연산자**다.
- `;`는 i3 명령을 연결하지만 이번에 검수한 별도 IPC 요청 경계를 만들지 않는다.
- `&&`는 첫 i3-msg 프로세스가 성공 종료한 경우에만 두 번째를 실행한다.
  모든 X11 이벤트가 안정화된다는 별도의 보장은 아니다.
- 기존 i3-msg와 셸만 사용하며 Python·별도 운영 스크립트·sleep·데몬은 추가하지 않는다.
- 단일 이동을 exec로 바꾸면서 외부 프로세스 실행 단계는 생긴다. 별도의 잠금은
  추가하지 않았으므로 의도적으로 빠르게 겹쳐 실행하는 동작은 최종 회귀에서 확인한다.
- 이미 검수된 키패드 쌍 이동은 그대로 i3 직접 명령으로 유지한다.

공통 mark begin/end 변수는 단일/쌍 이동 모두 재사용한다. `$move_one_to`는
단일 이동 명령 앞부분이다. set은 재귀 확장이 안 되므로 바인딩에서 각 변수를
직접 참조한다. 공백이 없는 현재 워크스페이스 이름은 변수 값의 불필요한
따옴표를 제거해 exec의 i3-msg 인자 안에서도 쓸 수 있도록 했다. 이름·번호·
모니터 배정 자체는 같다. 이름에 공백·따옴표·셸 특수문자를 추가한다면 이
exec 인용 방식도 다시 검토해야 한다.

예시 구조:

```i3
bindsym $mod+Shift+1 exec --no-startup-id \
    "i3-msg '$move_focus_begin; $move_one_to $right1' && \
    i3-msg 'workspace --no-auto-back-and-forth number $right1; $move_focus_end'"
```

검증: 가상 i3에서 실제 config를 로드하고 exec를 실제 키 이벤트로 실행했다.
마우스 추적을 켠 단일 이동 40개 조합, 기존 쌍 이동 20개 조합이 통과했다.
실제 세션에서는 수동 셸 명령 실험만 통과한 상태이며, config 단축키 적용은
사용자 리로드 후 검수한다. 가상 검사만으로 실제 해결을 확정하지 않는다.

1. `i3-msg reload`.
2. `Mod+Shift+F1`로 1→F1, `Mod+Shift+1`로 F1→1 이동.
3. 마우스를 움직이지 않아도 이동한 창에 입력되는지 확인.
4. 다른 숫자/F키와 0/F10, 기존 키패드 쌍 이동도 확인.

이번 커밋만 revert 후 reload하면 직전 단일 IPC 구현으로 돌아간다.
설정 revert가 실제 이동한 창까지 되돌리지는 않는다.

참고: [i3 exec와 인용부호](https://i3wm.org/docs/userguide.html#exec).

### 현재 완료 및 남은 최종 검수

`2221feb` 적용 후 사용자가 단일 창 이동·따라가기가 잘 작동함을 확인했다.
A1/A2를 완료로 기록한다. 새 기능 구현은 남지 않았다.

R1은 미완료다. 작업 중인 창을 종료하거나 자동 로그아웃하지 않고 다음을
사용자가 적절한 시점에 검수한다.

- 숫자/F키 개별 전환, Shift 개별 이동·따라가기, 키패드 쌍 전환·쌍 합류 이동.
- Num Lock 두 상태, 0/F10, 혼합 조합, 빈/기존 창이 있는 목적지, 같은 목적지 반복.
- 이동 후 임시 mark 정리와 기존 사용자 mark 보존, floating·일반 fullscreen.
- 빠른 연속 단일 이동에서 두 외부 IPC 실행이 겹치지 않는지. 문제가 있으면 이 항목만 따로 수정한다.
- 재로그인 또는 재부팅 후 배정·바인딩·시작 프로그램이 정상인지. 사용자 작업 보존은 별도이며 이 검사 때문에 자동 종료하지 않는다.

추가 Alt+Tab MRU는 별도 후속 논의다. 쌍 전환에서 출발 모니터 기억(F4)은
편익 대비 복잡도를 이유로 제외한 결정을 유지한다.


### 회귀 테스트 저장과 작성 시 실패 검증

사용자 요청에 따라 `/tmp`의 기능 테스트를 정리해
`tests/workspace_regression.py`와 [실행 안내](../tests/README.md)에 보존한다.
config 파일은 더 나누지 않는다. 운영 config 변경과 테스트 작성은 별도 커밋이다.

정상 설정에서 개별/쌍 전환 60개, 단일 이동 40개, 쌍 이동 20개, 총 120개
키 조합이 통과했다. Num Lock 두 상태를 실제 가상 키 이벤트로 실행한다.
기존 이전 도구 단위 테스트 6개도 통과했다.

테스트 작성 과정의 뮤테이션 검증은 `/tmp/i3-workspace-mutations/`에 만든
사본에서만 수행했다. 운영 파일은 변경하지 않았다.

| 임시 결함 | 실행 그룹 | 결과 |
|---|---|---|
| Shift+1의 목적지를 오른쪽 1 대신 2로 변경 | single | 실패(exit 1), 기대 창 위치 불일치 |
| Shift+1에서 두 번째 IPC 호출(전환·따라가기)을 제거 | single | 실패(exit 1), 포커스·내부 mark 정리 불일치 |
| 쌍 이동에서 mark 포커스 복원 제거 | pair | 실패(exit 1), 왼쪽 출발 창의 포커스 불일치 |

세 결함 모두 정상 i3 기동 후 기능 검사에서 실패했으며, 설정 문법 오류나
테스트 환경 기동 실패를 성공적인 실패 검증으로 간주하지 않았다.
변형 코드와 실행기는 `/tmp`에만 두고 커밋하지 않는다. 정상 회귀 테스트와
이 결과 기록만 보존한다. 이 검사는 이전 물리 환경 포커스 버그를 자동으로
재현했다는 뜻이 아니다.


### 같은 파일 안의 섹션 정리와 최종 자동 검수

사용자 지시에 따라 config 파일을 추가로 분리하지 않았다.
`workspaces.conf`를 다음 다섯 섹션으로 모았고 섹션 구분 주석을 추가했다.
쌍별 주석은 반복하지 않는다.

1. 워크스페이스 번호·표시 변수.
2. 공통 이동·포커스 명령.
3. 모니터 배정.
4. 숫자/F키/키패드 전환과 기존 Alt+Tab.
5. 숫자/F키/키패드 이동·따라가기.

유효 명령의 다중집합을 정리 전후 비교하여 주석·공백·순서만 바뀌었음을
확인했다. 변수는 모든 사용처보다 앞에 있고, 바인딩·공간 이름·출력 배정은
동일하다. 잘못 적힌 Ctrl+Tab 주석은 실제 바인딩대로 Alt+Tab으로 바로잡았다.

정리 후 저장된 회귀 테스트 전체 120개 조합과 i3 문법·diff 검사가 통과했다.
실행 중인 i3의 include 원문과 디스크 파일의 유효 명령도 동일했고,
`get_marks`에서 내부 `_i3_` mark가 남아 있지 않음을 확인했다.
이 검사는 읽기 전용이며 실제 세션에 자동 리로드나 창 이동은 하지 않았다.

R1 자동 검사는 완료했다. 사용자 작업을 종료하지 않고 재로그인/재부팅 후
확인만 남긴다. 다음에 사용자가 직접 로그인할 때 공간 배정과 단축키, 이동 후
따라가기, 시작 프로그램 중복이 없는지 확인하면 최종 마무리할 수 있다.

테스트의 고정 기대값은 번호/좌우/키코드 정책을 검증하기 위해 남기며,
config의 명시적인 키 매핑도 i3의 함수·반복문 부재에 따른 것으로 유지한다.
이 반복을 없애기 위한 운영 코드 생성기나 보조 스크립트는 추가하지 않았다.
