# Shift 쌍 이동 시 레이아웃 보존

## 상태

사용자가 빈 목적지 쌍으로 모든 창을 옮겨도 레이아웃이 풀린다고 보고한 개선을
진행했다. 가상 i3에서 재현·구현했고 자동 검사 후 실제 사용자 검수를 기다린다.
일반 숫자 전환·Mod+Tab·단일 창 이동의 기존 동작은 유지한다.

## 원인과 변경

기존 `$pair_move_all`은 `[workspace="__focused__"] move ...`로 창들을 각각
선택했다. 따라서 원래 분할의 부모·자식 구조와 비율을 통째로 옮기지 못했다.
새 레이아웃 검사는 이전 설정의 첫 빈 목적지 사례에서 구조·비율 불일치로 실패했다.

설치된 i3에서 실험한 결과, **워크스페이스 컨테이너 ID를 지정한 move**는
해당 공간의 tiling 트리를 하나의 묶음으로 이동한다. 출발 공간의 창을 일일이
선택하는 방식과 다르다.

```text
[con_id=<출발 workspace ID>] move --no-auto-back-and-forth container to workspace number 13:F3
```

i3 기본 명령으로 실제 이동을 수행한다. 출발 워크스페이스를 이름 변경하거나
출력 사이로 이동하는 방식은 사용하지 않는다. 왼쪽/오른쪽의 번호·표시·출력 배정은 유지한다.

## 구현 위치와 처리 순서

- `scripts/workspace-pair.py`에 `--move` 옵션과 `move_pair()`를 추가했다.
  기존 보조 프로그램 하나를 확장했으며 새 스크립트·서비스·패키지는 없다.
- config의 메인 Shift+숫자와 Shift+백틱을 이 옵션에 연결했다.
  예: `python3 ~/.config/i3/scripts/workspace-pair.py 3 --move`.
- 단일 창 이동에 사용하는 공통 mark 명령은 유지했다. 더 이상 쓰지 않는
  `$pair_move_all`은 제거했다.

처리 순서:

1. 현재 두 출력의 보이는 공간과 트리를 읽고 출발 workspace ID 두 개를 구한다.
2. 현재 선택한 창/컨테이너 ID를 잠시 메모리에 보관한다. 파일이나 mark로 저장하지 않는다.
3. 비어 있지 않고 목적지와 다른 공간만 workspace 컨테이너 단위로 이동한다.
4. 목적지 왼쪽과 오른쪽을 표시한 뒤 별도 IPC 요청으로 원래 컨테이너를 포커스한다.
5. 양쪽 목적지 표시를 확인한다. 부분 실패 시 오류를 알리며 역이동을 임의 수행하지 않는다.

쌍 전환과 같은 상태 파일의 잠금을 사용해 동시 실행을 직렬화하지만 **JSON 내용은
읽거나 갱신하지 않는다.** 상태 파일이 아직 없으면 잠금용 빈 파일이 처음 생길 수 있다.
이것은 previous/focus 이력을 생성하지 않으며, 이후 일반 전환에서 실제 위치를 기록한다.

## 보존하는 것과 합류 방식

- **빈 목적지:** 원래 창 순서·중첩 분할·내부 크기 비율을 한 묶음으로 보존한다.
- **기존 창이 있는 목적지:** 기존 창은 그대로 남고 출발 트리가 하나의 새 묶음으로 합류한다.
  묶음 안의 비율은 유지하지만 전체 목적지에서 차지하는 영역과 합류 위치는 i3가 배정한다.
- tabbed/stacking과 중첩 분할을 보존한다. 새 바깥 묶음 컨테이너가 생길 수 있다.
- floating 창은 floating으로 이동하며 일반 fullscreen 상태와 사용자 mark도 유지한다.
- 원래 포커스한 창을 따라간다. 선택된 창이 없는 빈 공간에서 출발하면 오른쪽 목적지로 끝난다.
- 한쪽 또는 양쪽이 이미 목적지면 그쪽은 다시 이동하지 않는다. 같은 목적지를 반복해도
  계속 새 바깥 묶음을 만들지 않는다.
- 창 교환은 하지 않는다. 숨겨진 다른 공간의 창은 이동하지 않는다.

화면의 절대 픽셀 크기·목적지 기존 창과의 전체 배치·출력 크기가 달라질 때의 위치를
원본 그대로 복제하는 기능은 아니다. 단일 창 이동은 기존 i3 삽입 동작을 유지한다.

## 검사

`tests/workspace_regression.py --group layout`을 추가했다.

- 출발 트리를 split과 실제 창 이동으로 구성하고 비율을 다르게 조정한다.
- 빈 목적지/기존 창이 있는 목적지 각각 splith·tabbed·stacking을 검사한다.
- 이동 전후 트리의 창 순서, 중첩 구조와 내부 percent를 비교한다.
  단일 자식으로 된 새 바깥 묶음은 비교에서 정규화한다.
- 기존 창 보존, 원래 창 포커스, 사용자 mark·floating·fullscreen 상태, 같은 목적지 반복을 검사한다.
- floating 창만 있는 경우와 양쪽 모두 비어 있는 경우도 검사한다.
- 이력 파일의 내용이 변하지 않는지 확인한다. 테스트용 창은 가상 i3에만 생성하고 정리한다.
- 새 검사를 먼저 작성했을 때 기존 설정은 빈 목적지의 첫 중첩 분할 사례에서 실패했다(exit 1).

전체 기존 회귀와 함께 실행하며 자동 검사와 실제 사용자 검수는 구분한다.

## 사용자 검수

먼저 `i3-msg reload`로 새 Shift 바인딩을 적용한다. 실제 작업 창 대신 구별되는
임시 터미널로 시작한다.

1. F1과 1에 각각 여러 창을 두고 가로/세로가 섞인 중첩 분할을 만든다. 크기 비율도 다르게 조절한다.
2. 비어 있는 목적지 쌍을 골라 Mod+Shift+숫자로 보낸다. 양쪽 원래 배치·비율이 유지되는지 본다.
3. 마우스를 움직이지 않고 원래 집중하던 창에 바로 입력할 수 있는지 확인한다.
4. 목적지에 기존 창을 먼저 둔 경우에는 기존 창과 이동한 묶음이 함께 남는지 확인한다.
5. 같은 목적지를 반복 선택해도 레이아웃이 추가로 바뀌지 않는지 확인한다.
6. tabbed/stacking, floating/fullscreen, 왼쪽/오른쪽 출발, 0/백틱과 Num Lock 두 상태를 확인한다.
7. Mod+숫자·Mod+Tab의 쌍별 포커스 복원과 단일 창 이동이 정상인지 확인한다.

체크할 항목은 [기능 검수표](workspace-review-checklist.md)의 레이아웃 보존 섹션에 있다.
설정을 되돌려도 이미 이동한 창 배치가 자동으로 원위치가 되지는 않는다.


자동 검사 결과:

- 전환 62개, 단일 이동 40개, 쌍 이동 22개, Mod+Tab 50개, 쌍별 포커스 42개,
  레이아웃 8개, 이력 40개로 총 264개 조합 통과.
- 이전 설정은 빈 목적지 레이아웃 검사에서 실패했고 개선 후 통과했다.
- 기존 이전 도구 단위 테스트 6개와 i3 문법·diff 검사를 함께 수행했다.
- 실제 리로드·레이아웃 검수는 사용자 확인을 기다린다.

복구가 필요하면 이번 기능 커밋을 revert한 뒤 reload한다. 상태 파일 형식은
JSON 그대로이므로 별도 상태 이전은 필요 없다. 이미 이동한 창과 배치는 직접
원하는 공간에 되돌린다.
